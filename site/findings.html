Benchmark

Jev finds more of the files a change needs.

Each test is a real past change from an open-source project: its commit message is the task, and the files it changed are the right answer. The tool sees the project as it was before the change, so it can't cheat. The score is simple: of the files the change really needed, how many did the tool put in its top 10?

Plain keyword search finds 69 of every 100 needed files. Jev finds 78. With the task written the way a developer would ask, it's 75 against 91. Laya, the local model, found fewer than keyword search.

A separate test asked whether that makes Claude Code faster. On 40 small changes, with Opus, it didn't: Claude found the files quickly on its own.

Project by project

Thirty tests per project. Jev ran on hono, rich, gin and prometheus. Laya ran on gin and httpx. ripgrep has keyword search only.

Is the difference real or luck?

With 30 tests per project, some difference would show up by chance alone. The line around each dot is the range the true difference plausibly sits in (a 95% bootstrap interval). When the whole line is right of zero, the gain is real; when it crosses zero, that project alone can't tell.

Across all four projects, Jev finds 9 more needed files per 100 than keyword search, somewhere between 4 and 15. Rewriting the file summaries for each language made no difference. Laya finds about 6 fewer than keyword search, between 2 and 10 fewer.

Top 5, 10 and 20

The gap is widest when the list is shortest. In the top five, Jev finds 69% of needed files and keyword search 56%.

Cost and time

Per test, from runs that weren't served from a cache. Jev's cost is its reported input tokens at $0.042 per million. Keyword search and Laya cost nothing but your CPU. Failed requests are Jev calls that returned an error; those files scored zero for that step and the ranking went on.

With realistic requests

Commit messages like "Fix case of GitHub" are harder to search with than what people actually type. So each test change was also rewritten as the request a developer would give an assistant, by a language model that saw the change but wasn't allowed to name its files or anything that only appears in the diff. 179 of 180 rewrites passed that check.

With realistic requests, Jev finds 16 more needed files per 100 in the top 10 than keyword search, plausibly between 11 and 22. The rewriter saw each change, so its wording may be a little more specific than a real person's; that helps both tools.

Does it make Claude Code faster?

Finding the right files is only useful if it saves the agent work. To check, Claude Code (Opus) made 40 of the test changes three times each, in a clean copy of the project: on its own, with the hook handing it Jev's file list, and with the file list plus the most relevant lines of code.

All three did about the same, and every difference is small enough to be luck. The closest to real is searching: with the file list and code, Claude searched 16% less, in a range from 33% less to 2% more. These changes were easy for Opus: about ten steps and a couple of searches each, so a list of suggestions had little to save. A 10-change trial run beforehand had looked better (a fifth fewer steps), which is why the full test was worth running.

What this doesn't rule out: help on large projects, on changes that span many files, or for weaker models that search less well. Those are the next tests.

Method and limits

  • Repositories are pinned to a commit: hono (TypeScript), rich (Python), gin (Go), prometheus (Go and TypeScript), httpx (Python), ripgrep (Rust).
  • Tasks: non-merge commits whose subject has at least four words, that modify one to five existing source files and add, delete or move none. Commits named like chores, releases, docs or refactors are skipped. Conventional-commit prefixes and PR numbers are stripped from the task text.
  • Tuning and test sets: a fixed order over eligible commits. The first 10 per project were used to make decisions, and the next 30 are the tests reported here, run once.
  • Commit messages are short and often vaguer than a real request to an agent. Finding the right files is also not the same as making the right change; this benchmark measures only the first.
  • Agent test: Claude Code with Opus, headless, one clean git worktree per run, the same tools and settings in every arm except the hook. 120 runs on 40 changes from hono, rich, gin and prometheus, with realistic requests. Scored on steps, tool calls, cost, time and whether it changed the files the real commit changed.
  • All file-finding runs together, including the per-language summaries that didn't ship, billed 68 million Jev input tokens, about $2.84.

Browse every task and both rankings in the run explorer.

Everything is reproducible from the repository: bench/mine.ts freezes the tasks, bench/run.ts runs a provider, and bench/report.ts writes the summary this page draws from. Jev responses are cached by request, so a replay is free.
