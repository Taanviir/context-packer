What 120 real changes showed

Jev found more of the right files than keyword search on three of four projects. An improvement I expected to help didn't, and the local model found fewer files than keyword search. The whole study cost about $2 of Jev usage.

The setup

A tool like this is only useful if the files it puts first are the ones the change needs. Git history already records that. So each test is a real past commit: its message is the task, the files it changed are the answer, and the tool sees the project as it was just before, so the answer can't leak in.

The score is one question: of the files the change needed, how many did the tool put in its top 10? If a change touched two files and both are in the top 10, that test scores 100%; one of them, 50%. The literature calls this recall@10.

Six projects, each frozen at one commit: hono (TypeScript, about 270 source files), rich (Python, 160), gin (Go, 73), prometheus (Go and TypeScript, 1,220), httpx (Python) and ripgrep (Rust). From each, a fixed order picks 10 changes for making decisions and 30 for testing, among commits that modify one to five existing files and add or delete none. Anything I tuned, I tuned on the first 10. The 30 test changes ran once per tool.

The main result

Over the 120 test changes on the four projects Jev ran on, the share of needed files each tool found:

ToolIn top 5In top 10In top 20Time per searchCost per search
Keywords56%69%79%53 ms$0
Jev69%78%88%2.5 s$0.007

So in the top 10, Jev finds 9 more needed files per 100. With 120 tests that could still be partly luck, so I checked with a bootstrap: the real gain is very likely between 4 and 15 per 100. In the top 5 it's 13 more (between 7 and 20). The gain is biggest where the list is shortest, which is where an agent looks first.

Project by project, Jev found 11 more per 100 on hono, 12 on rich and 14 on prometheus. Gin was a tie. Gin has only 73 source files and keyword search already found 87% of needed files there, so there was little left to find. The findings page has the ranges for each project, and the run explorer shows every test.

The idea that didn't work

The sketcher that summarizes each file for the wide pass looks for Kotlin keywords: class, fun, val, object. On a Python or Go file, that leaves little besides the path. Per-language rules looked like the obvious improvement, so I wrote them for TypeScript, Python, Go, Rust, C#, Swift and a few more, with docstrings and /// comments.

On the 10 changes per project used for decisions, they tied. On the test changes they tied again: within half a file per 100 of the simple summaries. And they cost more, because richer summaries are longer: 58% more on prometheus.

The reason is in the pool size. Up to 120 files get a full-source read, and on repositories of 70 to 1,200 files, that pool already holds most of the answers, chosen partly by BM25. The sketch pass only has to add a few files to the pool, and a path plus a file name often does that as well as a list of declarations. So the per-language sketcher didn't ship. It stays in the benchmark folder so the result can be reproduced. Sketches may matter on much larger repositories, but I didn't measure that.

The local model

Laya is a small model that runs on your own CPU, so no code leaves the machine. It scores a 60-file keyword shortlist, one short excerpt at a time. On gin and httpx it found 81% of needed files in its top 10, where keyword search found 87%: about 6 fewer per 100, very likely between 2 and 10 fewer. Each search took 27 seconds on httpx and 54 on gin, all of it CPU.

So Laya is only worth it when code must not leave the machine, and even then keyword search, which also runs locally, did better on these tests.

Faster keyword search, same answers

On a 14,004-file checkout of VS Code, a keyword pack took 4.2 seconds and 740 MB, most of it building a term map for every word of every file. BM25 only needs counts for the query's own terms and each file's length. Counting just those brought ranking from 2.8 to 2.0 seconds and memory to 620 MB, and the results on all 180 keyword tests came out identical.

Two bugs the benchmark found

  • Some Jev requests came back as HTTP 403 with an HTML page. The client reported "Jev rejected the API key", but the page was an edge firewall objecting to something in the source text. One such file cost its whole batch of six. Jev now reports it as rejected content, and the packer halves a rejected batch until only the offending file is lost.
  • The hook skipped "Stop writing to the SSE stream after the client aborts" as a conversational reply, because it starts with "stop". Only short prompts count as replies now.

Realistic requests

Commit subjects are short and sometimes cryptic, so I also rewrote every test change as the request a developer would type, with a language model that saw the change but wasn't allowed to name its files or anything that only appears in the diff. With those requests, keyword search found 75% of needed files in its top 10 and Jev found 91%. The gap grew from 9 to 16 per 100.

Large projects

The main projects are small to medium, so I added two large ones, taking changes only from when they were already big: vscode at about 11,300 source files and airflow at about 8,100. Jev found 60% of needed files in its top 10 on both; keyword search found 42% on vscode and 52% on airflow. A search took 4 to 5 seconds and 3 to 6 cents. Everything finds less in a codebase that size, but Jev's lead holds, clearly on vscode and within luck on airflow.

Does it make Claude Code faster?

This was the question that mattered most, so I tested it directly. Claude Code with Opus made 40 of the test changes three times each: on its own, with the hook giving it Jev's file list, and with the file list plus the most relevant lines of code.

The answer, for these changes: no. All three versions took about ten steps, cost about 20 cents and finished in about 40 seconds. With the hook, Claude changed the right files a little more often (80% against 77%) and searched a little less, but every difference was small enough to be luck.

The reason is that these changes were easy for Opus. It found the right files with a couple of quick searches, so a list of suggestions had almost nothing to save. It's like handing a map to someone who already knows the neighborhood. A trial run on 10 changes had looked better, with a fifth fewer steps; the full 40 showed that was mostly those 10 changes.

So the tool is good at its own job, putting the right files first, but that hasn't yet turned into a faster agent. Where it might: large projects where searching takes many steps, changes that touch many files, and weaker models. Those are the next tests.

What this doesn't show

  • The agent test measured steps, cost, time and which files changed, not whether each change was correct.
  • It used one strong model on small changes in projects of up to 1,200 files.

What it cost

Every Jev run, the rejected sketcher, the realistic requests and the large projects included, billed 169 million input tokens: about $7.08, which used up the account's credits. The 120 agent runs used about a quarter of a five-hour Claude plan window. Responses are cached by request body, so re-running the published numbers costs nothing. The cache is attached to the release.

Method, per-repository intervals and the raw tables are on the findings page.
